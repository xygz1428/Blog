# 踩坑记录

> 只记**真实发生过**的坑，每条含「现象 → 根因 → 解法 → 证据」。
> 目的：下次遇到同样症状，五分钟内能定位，而不是重新排查一遍。

---

## 1. `npm ci` 在 Linux CI 上失败，本地却正常

**现象**

GitHub Actions 的构建 job 在「Install dependencies」一步失败：

```
npm error `npm ci` can only install packages when your package.json and
npm error package-lock.json or npm-shrinkwrap.json are in sync.
npm error Missing: @emnapi/core@1.11.3 from lock file
npm error Missing: @emnapi/runtime@2.0.0-beta.2 from lock file
```

本地 `npm ci` 却完全正常（340 个包，退出码 0）。

**根因**

lockfile 在 **Windows** 上生成，`@emnapi/*` 是 Astro 图像处理链里的**平台相关可选依赖**。Windows 不解析它们，所以 lock 里只有引用、没有实体包条目。Linux runner 需要这些包，`npm ci` 的严格同步校验就判定「缺失」。

**解法**

CI 里把 `npm ci` 换成 `npm install --no-audit --no-fund`。`npm install` 会按当前平台解析，不做严格同步校验。

**代价**：放弃 lockfile 的严格复现性。对个人博客可接受。

**证据**：workflow 文件里保留了这段注释；换成 `npm install` 后 CI 连续三次通过。

## 2. 公式「结构对，但样式全无」

**现象**

构建产物里确实有 `class="katex"` 和 `katex-display`，验收检查也通过了。但页面上公式是一堆排不好的字符。

**根因**

**`katex.min.css` 从未被引入。** `rehype-katex` 只负责生成带 class 的 HTML，不负责样式。查 `dist/_astro/*.css` 里没有 `KaTeX_Main` 字体规则，说明样式表根本没打包。

**解法**

在 `BaseLayout.astro` 顶部加：

```js
import 'katex/dist/katex.min.css';
```

构建后 CSS 从 6.8 KB 变成 35.2 KB，并生成 19 个 woff2 字体文件。

**教训**

> **验收「结构存在」不等于「功能正常」。**
> 我当时只查了 `class="katex"` 在不在，就断定"公式渲染正常"——这是错的。应该查样式规则是否存在。

**证据**：产物 CSS 里搜 `KaTeX_Main`，修复前 0 命中，修复后命中。

## 3. 代码块双主题配置放错位置

**现象**

浅色模式下代码块也是深色（`#24292e` 背景 + 浅灰文字），压在暖纸底上非常突兀。

**根因**

配置写成了：

```js
syntaxHighlight: { type: 'shiki', themes: { light, dark } }   // ❌
```

`syntaxHighlight` 只认 `type` 和 `excludeLangs`。`themes` 是**非法键，被静默忽略**，Shiki 于是用了默认的 `github-dark`。

**解法**

主题必须放在 `shikiConfig` 里：

```js
syntaxHighlight: { type: 'shiki' },
shikiConfig: { themes: { light: 'github-light', dark: 'github-dark' }, wrap: true },
```

修复后 `<pre>` 带 `astro-code-themes` 类，内联浅色、深色走 `--shiki-dark` 变量。

**教训**：配置项写错**不会报错**，只会静默失效。改配置后必须验证产物，不能只看构建通过。

## 4. GitHub 直连不通（只有 github.com 一个域名）

**现象**

`git clone` 报 `Recv failure: Connection was reset` 或 `Failed to connect to github.com:443`。但浏览器能正常打开 GitHub，`npm install` 也正常。

**根因**

逐域名测试发现，**只有 `github.com` 不通**，其余全通：

| 域名 | 状态 |
|---|---|
| `github.com` | ❌ |
| `codeload.github.com` | ✅ |
| `raw.githubusercontent.com` | ✅ |
| `api.github.com` | ✅ |
| `ssh.github.com` | ✅ |

浏览器走的是系统代理，而 **git 命令行不继承系统代理**。

**解法**

只给 github.com 配代理（不影响其他站点）：

```powershell
git config --global http.https://github.com.proxy http://127.0.0.1:7897
```

或用 API 取文件（`api.github.com` 通）、或从 `codeload.github.com` 下 zip。

**注意**：npm 的 registry 本来就通，**不要**给它也配代理——代理一停 npm 就废。

## 5. 批量替换误伤命名

**现象**

把项目从 `KBlog` 改名成 `Blog` 时，用了一次性批量替换：

```
-replace 'KBlog','Blog'
```

结果 `localStorage` 的键 `kblog-theme` 变成了 `Blog-theme`（大写 B）。

**根因**

替换规则没考虑大小写与词边界。`kblog-theme` 里不含 `KBlog`，但后续 `-replace 'kblog-theme','blog-theme'` 与 `'KBlog','Blog'` 的执行顺序/大小写组合产生了非预期结果。

**影响**

功能没坏（读写用的是同一个错键），但命名不规范，且与代码里其他 `kebab-case` 约定不一致。

**解法**

两个键统一改成 `blog-theme`。

**教训**：批量替换后**必须逐文件复核**，尤其是字符串常量。改完用 `grep` 反查一遍旧值。

## 6. 子路径下的绝对路径必然 404

**现象**

文章里写 `![](/images/demo.png)`，部署后图片加载失败。

**根因**

站点部署在 `https://<用户名>.github.io/Blog/` 这个**子路径**下。`/images/...` 指向域名根，不在 `/Blog/` 下。

**解法**

- 图片放 `src/content/blog/images/`
- Markdown 里用相对路径 `![](./images/demo.png)`
- 构建时 Astro 自动补 base 前缀并生成哈希文件名

**证据**：产物里 `src="/Blog/_astro/demo-flow.CKJBRs3P_Z19o4Wk.webp"`，带 `/Blog/` 前缀。

**同类风险**：手写的 `href="/blog/"` 也会漏 base。代码里统一用 `withBase()` 包装（见 `src/utils/url.ts`）。

## 7. PowerShell 里 `$HOME` 是只读变量

**现象**

验证脚本里写了 `$home = ...ReadAllText(...)`，赋值报错但脚本继续跑，后面的检查拿 `$HOME`（用户目录路径字符串）去匹配 HTML，得出**假的 False**。

**根因**

`$HOME` 在 PowerShell 里是只读自动变量，赋值失败后变量仍是原值。

**解法**

换个名字（如 `$homeHtml`）。同理要避开 `$PWD`、`$PID` 等自动变量。

**教训**：脚本报错但继续执行时，后续判断可能建立在**错误的值**上——看起来"检查通过/失败"其实无效。这类假阴性比直接报错更危险。
