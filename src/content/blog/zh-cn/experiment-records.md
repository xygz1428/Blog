实验记录最大的问题是：**记录时觉得够了，回看时发现缺关键信息**。

三个月后你打开一个叫 `result_final_v3.csv` 的文件，完全想不起来它是哪组参数跑出来的。

## 最小字段清单

每次实验至少记这些：

| 字段 | 为什么必须有 |
|---|---|
| 时间 | 定位到具体那次运行 |
| 目的 | 这次想验证什么假设 |
| 变量 | 改了什么，其余保持什么 |
| 参数全量 | 不只是改动的，**全部**参数值 |
| 数据版本 | 用的是哪份数据、哪个版本 |
| 代码版本 | Git commit hash，不是「最新版」 |
| 运行环境 | 依赖版本、硬件、随机种子 |
| 结果 | 原始输出 + 关键指标 |
| 异常 | 报错、警告、跑得特别慢的地方 |
| 结论 | 一句话：假设成立/不成立/不确定 |

## 三个最容易漏的

### 1. 随机种子

没有种子，结果不可复现。机器学习实验尤其如此——同一份代码换个种子，指标可能差几个百分点。

**记法**：把种子写进配置，配置整体存档，而不是只记「seed=42」。

### 2. 失败的那几次

人只记得成功的那次，但**失败记录往往更有价值**——它能告诉你哪条路走不通，省掉重复试错。

建议单独一个「失败记录」文件，每次失败写一行：什么配置、什么现象、猜测的原因。

### 3. 当时的判断

跑完实验时你脑子里有个解释，比如「这个下降应该是学习率太大」。这个判断如果没写下来，两周后看到同样的曲线，你会重新猜一遍。

**记法**：结果旁边写「我的解释是……」，并标明这是推测而非结论。

## 目录结构建议

```
experiments/
├── 2026-11-16-lr-sweep/
│   ├── README.md          # 目的、变量、结论
│   ├── config.yaml        # 完整参数
│   ├── result.csv         # 原始输出
│   ├── notes.md           # 当时判断、异常、下一步
│   └── figures/           # 图
```

一个实验一个目录，**目录名带日期**。这样 `ls` 就是时间线。

## 记录的成本控制

全量记录听起来很累，实际能自动化大半：

- 配置：跑实验的脚本里直接 `dump` 参数到 `config.yaml`
- 代码版本：`git rev-parse HEAD` 写进结果文件
- 环境：`pip freeze` 或 `conda list` 存一份

剩下的手写部分只有「目的」「当时的判断」「结论」——这三样恰好是最需要人写的。

## 怎么判断记录够不够

一个实用测试：**假设别人拿着你的记录要重跑这个实验，他能跑出来吗？**

如果他会问你「数据在哪」「用的什么参数」「跑了几次」，那说明记录不够。

## 一个反直觉的建议

**先写结论，再补过程**。

跑完实验趁着记忆新鲜，先写三行结论和当时的判断，细节可以后补。反过来做的话，等你整理完数据，已经忘了当初为什么这么设计。

## 小结

| 项 | 记不记 |
|---|---|
| 全部参数 | ✅ 必须（自动化） |
| 随机种子 | ✅ 必须 |
| 代码 commit | ✅ 必须 |
| 失败实验 | ✅ 强烈建议 |
| 当时的判断 | ✅ 强烈建议 |
| 中间过程日志 | ⚠️ 保留但不必整理 |
