每次有人问「你的博客用什么数据库」，我都回答：没有数据库。对方的反应通常是「那文章存在哪」。

答案很简单：**存在 Git 仓库里，一个 Markdown 文件一篇**。

## 数据库在博客里负责什么

传统博客（WordPress 那类）用数据库是因为要解决三件事：

1. **存储**：文章正文、元数据
2. **查询**：按分类、标签、时间筛选
3. **写入**：在后台编辑器里保存

静态站把这三件事分别换掉了：

| 需求 | 数据库方案 | 静态站方案 |
|---|---|---|
| 存储 | 数据库表 | Markdown 文件 + Git |
| 查询 | SQL 查询 | **构建时**算好，生成静态页面 |
| 写入 | 后台表单 | 编辑器改文件 + `git push` |

## 关键洞察：查询可以在构建时做

博客的查询有个特点——**读者看到的内容，对所有人是一样的**。

「最新 10 篇文章」「技术分类下所有文章」这类结果，不需要在每次请求时算一遍。构建时算好，生成成静态 HTML 就行。

这就是静态站能成立的根本原因：**读多写少，且读的结果可以预先算**。

一旦出现「每个用户看到不同内容」的需求（比如登录后的个人推荐），静态站就不够了——那是另一类问题。

## 换来的好处

**1. 没有可攻击的后端**

没有数据库连接、没有 SQL 注入、没有会话管理、没有后台登录页。攻击面从「一整台服务器」缩到「几个静态文件」。

**2. 部署成本接近零**

构建产物是一堆 HTML/CSS/图片，放在任何静态托管上都能跑。GitHub Pages 免费，而且不需要维护服务器、不需要打补丁。

**3. 内容天然有版本历史**

`git log` 就是修订记录，`git diff` 就是改动对比。误删了能恢复，改错了能回滚——这些在数据库方案里要额外做。

**4. 本地就是完整环境**

`npm run dev` 起一个本地服务器，行为和线上一致。不需要装 MySQL、不需要导入数据。

## 代价（必须承认）

**1. 构建时间随内容线性增长**

100 篇文章构建约 2 秒，10000 篇可能要几分钟。超过一定规模就得考虑增量构建。

**2. 没有实时交互**

评论、点赞、搜索建议这类需要服务端的，得接第三方（如 Giscus 基于 GitHub Discussions）。

**3. 写作需要会 Git**

这是最大的门槛。对只想写字的人，得先教会 `git add / commit / push`，或者做个脚本封装。

## 什么情况下该换

如果你的需求变成下面任意一条，静态站就不合适了：

- 需要用户登录、个性化内容
- 内容量大到构建时间不可接受，又不想做增量构建
- 需要复杂的后台工作流（多角色审核、定时发布）

否则，静态站是维护成本最低的选择。

## 小结

数据库解决的是「动态查询与并发写入」。博客这两个需求都很弱：查询可以预计算，写入频率是每天几篇。

**把不需要的东西去掉，比优化它更有效。**
