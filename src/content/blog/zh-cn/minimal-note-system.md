做笔记最容易掉的坑是：**花两周研究工具，然后一个字没记**。

这篇讲的方案非常朴素，但它能立刻开始用。

## 从需求倒推

先问自己：笔记要解决什么问题？

我的答案是三个：

1. **记住待办**——不然会忘
2. **找到旧结论**——三个月前想过什么
3. **沉淀可复用的东西**——方法、结论、代码片段

这三个需求对结构的要求完全不同。把它们混在一个体系里，是大多数笔记系统崩溃的原因。

## 三个文件

```
inbox.md      —— 所有临时想法先扔这里，不分类
projects.md   —— 进行中的事，每个三行：目标 / 下一步 / 卡点
notes/        —— 值得长期留的，一个主题一个文件
```

就这三个。

**`inbox.md`** 是关键。想法冒出来时不要纠结放哪，先扔进去。分类留到整理时做——**分类成本高是笔记系统死亡的第一原因**。

**`projects.md`** 只记进行中的。做完就移走，保持短。它回答「我现在该做什么」。

**`notes/`** 存沉淀下来的内容。每个文件一个主题，文件名就是主题名。

## 一条规则

**每周清一次 inbox。**

- 做完的事 → 删掉
- 有长期价值的 → 整理进 `notes/`
- 要做的 → 移到 `projects.md`
- 不确定的 → 留着，下周再判断

清空 inbox 的动作比任何分类体系都重要。它保证系统不会烂掉。

## 为什么不建议一开始就建标签体系

标签系统看起来很美，实际上有三个问题：

1. **同一件事可以用五个标签描述**，你会纠结用哪个
2. **标签会膨胀**，三个月后你有一百个标签，找不到东西
3. **维护成本随笔记量线性增长**

替代方案：**用文件名和全文搜索**。

现代编辑器和系统搜索都能全文检索。给文件起个好名字（包含关键词），比一百个标签管用。

## 什么内容值得进 `notes/`

判断标准只有一条：**三个月后我还会想找它吗？**

- 会的 → 进 notes
- 不会 → 用完就删

比如：

| 内容 | 去处 |
|---|---|
| 今天会议的结论 | inbox（下周清掉或转项目） |
| 某个工具的具体配置步骤 | notes（会反复用） |
| 读完一篇文章的感想 | inbox，多半会删 |
| 一个可复用的代码片段 | notes |
| 待办事项 | projects |

## 工具选择

**任何支持纯文本 Markdown 的编辑器都行。**

关键不是工具，是文件在**你的磁盘上、纯文本、能被 Git 管**。这样：

- 换工具不丢数据
- 能用 grep 搜索
- 能版本管理

反面例子：把笔记只存在某个云端服务的私有格式里。工具一停服，数据就没了。

## 常见失败模式

| 症状 | 原因 | 解法 |
|---|---|---|
| 记了一堆从不回看 | 没有清理动作 | 每周清 inbox |
| 找不到东西 | 分类太细 | 改用全文搜索 |
| 建了一堆空文件 | 先建结构后填内容 | 从三个文件开始 |
| 换工具时数据丢了 | 用了私有格式 | 纯文本 + Git |

## 小结

最小可用方案的核心不是「三个文件」这个数字，而是两条原则：

1. **先捕获，后整理**（降低记录成本）
2. **定期清空**（防止系统腐烂）

体系是长出来的，不是设计出来的。先跑三个月，你会发现哪些结构真的需要。
